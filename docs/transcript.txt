     COMS3011A Lab 1 — Local-First Todo App

     Context

     This is a university assignment (due 2026-08-04) graded on a strict rubric
     — see lab_one.pdf in the working directory for the full brief. Key scoring
     pressures that shape this plan:

     - Commit history (18 marks): penalized heavily for "whole app in 1-2
     commits" or a single-sitting dump. We must build incrementally, one
     coherent working slice per commit, across more than one session.
     - Database design (16 marks): overdue must be derived at read time from due
     date + status, never stored as a column/status. Archive must be a
     flag/timestamp on the task row, never a copy to another table/file.
     - Testing (12 marks): 3+ tests exercising real behavior (not smoke tests),
     run against a throwaway DB via one documented command, including coverage
     of archiving and the overdue rule.
     - Documentation (18 marks): three markdown sections — Third-Party Code
     (deps + why), Database Design (tables + relationships), Running It (Node
     version + exact commands, verified from clean clone).
     - AI usage (8 marks): transcripts must show constraints stated up front and
     at least one instance of rejecting/correcting an AI output — this happens
     naturally through normal collaboration, not staged.
     - Functional walkthrough (28 marks): create/edit/archive tasks, sort by
     topic/status/due-date, overdue flagged, restart persistence — all from a
     clean clone via README alone.

     User has confirmed via AskUserQuestion:
     1. Layout: Sidebar (dark, sections: Overdue / Due Tomorrow / All Tasks
     grouped by topic) + main panel with sortable list — inspired by the
     uploaded Morgen-style screenshot's visual language (dark sidebar, colored
     status/priority pills, clean panels), NOT its calendar-grid mechanics.
     2. Pages: Three-plus pages — / (active task list), /task/[id] (detail/edit
     page), /task/new (create), /archive (archived tasks).
     3. Stack: Next.js App Router + better-sqlite3 + Drizzle ORM.

     Tech Stack & Why (for later Third-Party Code doc)

     - next (App Router) — required by brief.
     - better-sqlite3 — synchronous SQLite driver, no native build flakiness
     under grading, required by brief.
     - drizzle-orm + drizzle-kit — typed schema/migrations, makes "Database
     Design" doc trivial to keep accurate, easy to point a throwaway DB at for
     tests.
     - vitest — fast, native ESM/TS support, works well for testing API route
     handlers and DB logic without a browser.
     - tailwindcss — fastest way to hit the dark sidebar + card aesthetic from
     the screenshot without hand-rolling CSS.
     - No auth libs, no state-management libs (React state + server actions/API
     routes are enough for single-user local app).

     Data Model

     Single tasks table (SQLite via Drizzle):

     ┌─────────────┬─────────────────────────────────────┬─────────────────────┐
     │   Column    │                Type                 │        Notes        │
     ├─────────────┼─────────────────────────────────────┼─────────────────────┤
     │ id          │ integer PK autoincrement            │                     │
     ├─────────────┼─────────────────────────────────────┼─────────────────────┤
     │ title       │ text not null                       │                     │
     ├─────────────┼─────────────────────────────────────┼─────────────────────┤
     │ description │ text                                │ nullable            │
     ├─────────────┼─────────────────────────────────────┼─────────────────────┤
     │ due_date    │ integer (unix ms) or text (ISO)     │ not null            │
     ├─────────────┼─────────────────────────────────────┼─────────────────────┤
     │ topic       │ text not null                       │ free-text           │
     │             │                                     │ topic/category      │
     ├─────────────┼─────────────────────────────────────┼─────────────────────┤
     │ status      │ text not null, check in             │ fixed enum, default │
     │             │ ('todo','in_progress','complete')   │  'todo'             │
     ├─────────────┼─────────────────────────────────────┼─────────────────────┤
     │             │                                     │ null = active;      │
     │ archived_at │ integer (unix ms) nullable          │ timestamp =         │
     │             │                                     │ archived. This is   │
     │             │                                     │ the archive flag.   │
     ├─────────────┼─────────────────────────────────────┼─────────────────────┤
     │ created_at  │ integer not null default now        │                     │
     ├─────────────┼─────────────────────────────────────┼─────────────────────┤
     │ updated_at  │ integer not null default now        │                     │
     └─────────────┴─────────────────────────────────────┴─────────────────────┘

     - Overdue is never stored — computed as due_date < now() && status !== 
     'complete' && archived_at is null, both in API responses and at display
     time. Document this explicitly.
     - Archive = set archived_at, never delete, never copy rows. Archived tasks
     remain fetchable via /archive.
     - Single table is sufficient — no relationships needed (topic/status are
     plain columns, not FK'd lookup tables), which keeps the "Database Design"
     doc simple and defensible. Sorting by topic/status/due-date is just ORDER 
     BY.

     Routes / Pages

     - GET / — active task list (archived_at IS NULL), sort controls
     (topic/status/due-date), sidebar with Overdue count, Due Tomorrow count,
     topic groupings. "New Task" entry point.
     - GET /task/new — create form (title, description, due date, topic; status
     defaults to Todo).
     - GET /task/[id] — edit form (all fields editable, status changeable among
     the 3 fixed values, "Archive" action button).
     - GET /archive — archived tasks, read view (view-only list, maybe allow
     unarchive later if time permits but not required by brief).

     API Routes (Next.js Route Handlers, app/api/tasks/...)

     - GET /api/tasks?sort=&status=&topic= — list active tasks, computed overdue
     field included per task.
     - GET /api/tasks/archived — list archived tasks.
     - POST /api/tasks — create.
     - GET /api/tasks/[id] — fetch one.
     - PATCH /api/tasks/[id] — edit fields and/or status.
     - POST /api/tasks/[id]/archive — set archived_at = now.

     Route handlers are the thin layer; DB logic lives in lib/db/tasks.ts so
     it's directly unit-testable without spinning up HTTP.

     UI Design Direction (from screenshot, adapted)

     - Dark sidebar (fixed width, dark bg) containing: app title, "Overdue"
     section with count badge (red, matches screenshot's red badge), "Due
     Tomorrow" section, "All Tasks" section listing topics as filters, link to
     Archive, "+ New Task" button.
     - Main panel: light/neutral content area, task list as rows/cards showing
     title, topic pill, status pill (color-coded: Todo=gray, In-Progress=blue,
     Complete=green), due date, red "Overdue" flag badge when applicable (NOT a
     4th status — purely visual).
     - Sort control bar above the list (topic / status / due date,
     ascending/descending).
     - Status and topic rendered as colored pill badges, echoing the
     screenshot's colored dot/pill sidebar icons and task tags.

     Build Plan — Commit Sequence

     Each numbered item = one commit, each leaves the app in a working state.
     Session breaks noted so history isn't a single-sitting dump.

     Session 1 — scaffold & data layer
     1. chore: scaffold Next.js app with TypeScript + Tailwind —
     create-next-app, base config, .gitignore (exclude *.db, node_modules).
     2. feat: add SQLite schema and Drizzle setup — drizzle.config.ts,
     lib/db/schema.ts (tasks table), migration generation, lib/db/client.ts
     (opens data/app.db, creates dir if missing).
     3. feat: add task data-access layer with derived overdue logic —
     lib/db/tasks.ts: listActive(sort), listArchived(), getById(), create(),
     update(), archive(), plus a pure isOverdue(task) helper. Include first
     vitest tests here against a throwaway test DB (:memory: or temp file) —
     covers create, overdue derivation, archive-hides-from-active.

     Session 2 — pages & layout
     4. feat: add app shell with sidebar layout inspired by reference design —
     root layout, sidebar component (static counts/links first), Tailwind theme
     tokens (dark sidebar palette, pill colors).
     5. feat: build active task list page with sort controls — / page wired to
     GET /api/tasks, sort by topic/status/due-date, status + overdue pill
     rendering.
     6. feat: add task creation form and API route — /task/new + POST 
     /api/tasks.
     7. feat: add task edit page with archive action — /task/[id] + PATCH and
     POST /archive routes.
     8. feat: add archive page for viewing archived tasks — /archive + GET 
     /api/tasks/archived.
     9. feat: wire sidebar counts and topic filters to live data — Overdue/Due
     Tomorrow counts, topic list from distinct topics in DB.

     Session 3 — polish, tests, docs
     10. test: add coverage for edit, archive, and sorting behavior — round out
     to comfortably 3+ meaningful tests (create/read, overdue derivation,
     archive transition, sort correctness).
     11. docs: add third-party code, database design, and running-it docs —
     docs/ markdown files per brief spec.
     12. chore: verify clean-clone install/run/test flow — actually delete
     node_modules + db file and redo the documented steps, fix anything broken.

     (Additional small commits are fine/expected if fixes are needed along the
     way — the rubric wants coherent slices, not exactly 12.)

     Testing Approach

     - Vitest, testing lib/db/tasks.ts functions directly (not through HTTP)
     against a fresh SQLite file/:memory: DB created in beforeEach, migrated via
     Drizzle, and torn down after — never touching the dev data/app.db.
     - Minimum required coverage: create+list, overdue derivation (past due +
     not complete = overdue; complete = not overdue; future due = not overdue),
     archive (archived task disappears from active list, remains in archived
     list).
     - Single documented command: npm test.

     Verification (end of build)

     1. rm -rf node_modules data/app.db then follow README from scratch: install
     → migrate/init DB → npm run dev → confirm app loads.
     2. Manually walk the 7-step functional checklist from the brief (create
     task w/ 4 fields, edit + reload persists, archive removes from active but
     stays viewable, sort by each of the 3 keys, overdue flag shown and not a
     status, restart persists data).
     3. npm test runs and passes from clean clone.

     Open Items to Confirm Nothing Was Missed

     None outstanding — stack, layout, and page structure already confirmed by
     user. Ready to scaffold on approval.
